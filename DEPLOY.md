# Размещение Tutorina на VPS

Подготовлен вариант для одного сервера и одного backend. Публичный запуск ещё не выполнен.
Пока домена нет, проверяйте приложение через SSH-туннель: запускайте локальный
Compose с `APP_PORT=127.0.0.1:18080` и подключайтесь с компьютера командой
`ssh -L 18080:127.0.0.1:18080 пользователь@VPS`. Откройте `http://localhost:18080`.
Для этого варианта нужен отдельный `.env` с сильным паролем БД; порт сайта наружу
не открывается. Не вводите ключ через публичный HTTP по IP. После покупки домена
production начнёт с отдельной базой: перенос расписания выполняется через dump.

Docker Compose **2.24.4 или новее** нужен для `!override`: production публикует только
80 и 443 вместо локального 18080. Backend, frontend и PostgreSQL доступны только
в Docker-сети. Проект `tutorina-prod` использует отдельные тома от локальной разработки.

## Сервер и домен

Установите Docker Engine и Compose plugin. Настройте SSH по ключу и firewall:
SSH, TCP 80/443 и UDP 443. Не открывайте 5432 и 8081. Создайте DNS A для домена
на IPv4 сервера; AAAA добавляйте только при работающем IPv6. Порты 80/443 должны
быть свободны. Caddy получает и продлевает сертификаты автоматически.

Поместите репозиторий на сервер. Все дальнейшие команды выполняются из его корня:

```bash
cp .env.production.example .env.production
chmod 600 .env.production
openssl rand -hex 32
```

Внесите сгенерированный пароль в `DB_PASSWORD`, свой домен без `https://` в
`APP_DOMAIN` и адрес для ACME в `ACME_EMAIL`. Файл исключён из Git.
Не используйте локальную `.env` на сервере. Не выводите полный `compose config`
в общедоступные логи — он содержит пароль БД.

## Первый запуск

```bash
./scripts/prod config --quiet
./scripts/prod build --pull
./scripts/prod up -d --wait
./scripts/prod ps
./scripts/prod exec -T backend ./tutorina-key
```

Последняя команда выдаёт ключ один раз. Сохраните его в менеджере секретов.
Повторный запуск заменяет ключ и отзывает сессии, поэтому не включайте его в
обычные обновления. Команды используют фиксированное имя проекта для стабильных томов.

Проверьте `https://ВАШ-ДОМЕН/`, `/login`, `/admin` и `/admin/directions`.
Без ключа изменения должны возвращать 401. Проверьте создание направления и
слота, публикацию на доске и выход. HTTP должен перенаправляться на HTTPS.

```bash
curl --fail https://ВАШ-ДОМЕН/api/v1/ping
./scripts/prod logs --tail=100 backend caddy
```

Caddy не включает access log; приложение не записывает ключи, токены,
тела запросов и IP. Docker-логи ограничены тремя файлами по 10 МБ на сервис.
CSP разрешает inline-стили для Material UI, но не inline-скрипты.

## Резервные копии

```bash
./scripts/backup
```

Создаёт атомарный PostgreSQL dump в `backups/` с правами только владельца.
Он содержит расписание, хеш ключа и сессии. Храните копии с ограниченным доступом
и регулярно переносите их вне VPS. Например, ежедневный cron (замените путь):

```cron
0 3 * * * /opt/tutorina/scripts/backup >> /opt/tutorina/backups/cron.log 2>&1
```

Предварительно создайте каталог `backups` с правами 700. Время cron зависит от
часового пояса сервера. Установите срок хранения после выбора хранилища;
автоматическое удаление копий сейчас не настроено. Том `caddy_data` содержит
сертификаты: сохраняйте его при обновлениях. Копируйте `.env.production` отдельно
в защищённое хранилище, а не в Git.

Сначала проверьте восстановление в **отдельную** тестовую БД:

```bash
./scripts/prod exec -T postgres sh -c 'createdb -U "$POSTGRES_USER" tutorina_restore_check'
./scripts/prod exec -T postgres sh -c 'pg_restore -U "$POSTGRES_USER" -d tutorina_restore_check --exit-on-error --no-owner --no-acl' < backups/ИМЯ.dump
./scripts/prod exec -T postgres sh -c 'psql -U "$POSTGRES_USER" -d tutorina_restore_check -c "SELECT count(*) FROM slots;"'
./scripts/prod exec -T postgres sh -c 'dropdb -U "$POSTGRES_USER" tutorina_restore_check'
```

Для реального восстановления остановите backend, сделайте копию текущей базы,
восстановите проверенный dump в новую базу и переключите `DB_NAME` у приложения
и мигратора; не удаляйте рабочую базу до проверки. После восстановления создайте
новый ключ, чтобы отозвать сессии из резервной копии.

## Обновления

Запишите текущую версию (`git rev-parse HEAD`) и подготовьте новую версию кода.
Затем:

```bash
./scripts/prod build --pull
./scripts/backup
./scripts/prod stop backend
./scripts/prod run --rm --no-deps migrate
./scripts/prod up -d --wait
./scripts/prod ps
```

Обновление предполагает короткий перерыв. Если миграция не прошла, не запускайте
новый backend; изучите ошибку. Возврат к старому коду возможен только при совместимой
схеме; для несовместимых изменений потребуется восстановление проверенной копии.
Не используйте `down --volumes`: это удаляет базу и сертификаты.
Изменение `DB_PASSWORD` в env не меняет пароль существующего PostgreSQL автоматически.

Образы собираются на сервере; реестр и CI/CD пока не настроены. Перед первым
публичным запуском обновите базовые образы и зависимости с проверкой сборки и
уязвимостей. Сейчас приложение, мигратор и генератор ключа используют один
DB-пользователь с широкими правами; разделение ролей — отдельное усиление.
Для нескольких экземпляров backend нужен общий лимит входа вместо текущего
счётчика в памяти. Для этого небольшого приложения оставляйте один backend.

Официальные справки: [Caddy HTTPS](https://caddyserver.com/docs/quick-starts/https),
[Compose merge и !override](https://docs.docker.com/reference/compose-file/merge/).
